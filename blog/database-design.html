Database Design for Scalable Apps

Published: March 12, 2026 • 7 min read

Database design is the foundation of application scalability. No amount of application-level caching or optimization can compensate for a poorly designed database schema. Whether you're using PostgreSQL with Supabase, MySQL, or any relational database, the principles of good schema design remain consistent: normalize for data integrity, denormalize strategically for performance, index based on query patterns, and plan for migrations from day one.

Normalization is the starting point. I aim for third normal form as a baseline: every table has a primary key, all non-key attributes depend on the entire primary key, and no transitive dependencies exist. For multi-tenant applications like EAT O'CLOCK, every table includes a tenant_id column that forms part of a composite primary key, ensuring data isolation at the database level. Foreign key constraints with ON DELETE CASCADE or ON DELETE SET NULL maintain referential integrity when parent records are removed. I use PostgreSQL enums for status fields rather than string or integer codes — they provide type safety at the database level and are self-documenting. However, I avoid over-normalization: if a join becomes too expensive for a frequently accessed query pattern, I add a denormalized column with application-level logic to keep it in sync.

Indexing strategy can make or break query performance. I analyze the application's query patterns before creating indexes — every index adds write overhead, so unused indexes are worse than no indexes. For the orders table, I created a composite B-tree index on (tenant_id, status, created_at DESC) because the most frequent query is "show recent orders for this tenant, filtered by status." I use partial indexes for filtered queries: CREATE INDEX idx_active_orders ON orders(status) WHERE status NOT IN ('cancelled', 'delivered'). For full-text search across menu items and product descriptions, I use PostgreSQL's GIN index with the to_tsvector function. The EXPLAIN ANALYZE command is my go-to tool for verifying that queries use the expected indexes — I run it on every new query before deploying to production.

Database migrations should be version-controlled and automated. I use Supabase migrations (which are plain SQL files) to manage schema changes. Every migration is a file with a timestamp prefix, and I never modify a migration that has already been applied to production. Instead, I create a new migration that alters the schema. For zero-downtime migrations, I follow a expand-migrate-contract pattern: first add the new column or table (expand), backfill data and update the application to use both old and new structures (migrate), then remove the old column (contract). This approach allows the application to run safely during the migration window. I also set up database backups with point-in-time recovery and test the restore process regularly. A well-designed database, with proper indexing and migration practices, will scale gracefully from hundreds to millions of records without major rewrites.
