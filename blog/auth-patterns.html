Authentication Patterns in Next.js

Published: February 10, 2026 • 7 min read

Authentication is one of the most critical and error-prone aspects of web development. In a Next.js application, you have multiple rendering environments — server components, client components, API routes, and middleware — each requiring a different approach to auth. Getting it wrong can lead to security vulnerabilities, poor user experience, or both. The key is choosing the right authentication strategy for your application's needs and implementing it consistently across all layers.

For most applications, I recommend Auth.js (formerly NextAuth.js) v5 as the authentication foundation. It supports over 80 OAuth providers, credential-based auth, and database sessions out of the box. The v5 rewrite aligns perfectly with the App Router, providing server component actions, middleware integration, and edge-compatible session handling. For the EventPass project, I used Auth.js with Google OAuth and magic link authentication — users can sign in with a single click or receive a one-time link via email. The session is stored in a PostgreSQL database via Supabase, and the Auth.js adapter handles all the plumbing. Middleware protects API routes and dashboard pages, while public pages remain accessible. The auth() helper function can be called in server components and API routes to get the current session without any client-side setup.

JWT-based authentication is a lighter alternative suitable for APIs and mobile apps. When using JWTs, the key considerations are token storage, refresh token rotation, and revocation. I store access tokens in memory and refresh tokens in httpOnly, secure, sameSite cookies. The access token has a short expiry (15 minutes), while the refresh token lasts 7 days. A middleware function intercepts 401 responses, attempts token refresh, and retries the original request transparently. For server-side rendering, the JWT payload should be decoded server-side and passed as a prop — never expose the raw token to client components. The jose library is my preferred JWT implementation because it works in edge runtimes and supports all modern algorithms.

Role-based access control (RBAC) adds another layer of complexity. I implement a permission matrix with roles like admin, editor, and viewer, each with granular permissions. The permissions are encoded in the session or JWT and checked at three levels: middleware for route protection, server components for data access, and API routes for mutations. Next.js middleware is particularly powerful — it runs before the request reaches the page, so unauthorized users can be redirected before any content renders. For the EAT O'CLOCK admin dashboard, middleware checks for the admin role on all /admin/* routes, while server component checks ensure even if a user navigates directly to a data-fetching endpoint, they only see their authorized data. Defense in depth — never rely on a single layer of auth enforcement.
